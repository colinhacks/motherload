# Motherload: design record

Each section is one decision: what was decided, the alternatives weighed, and the evidence. Decisions taken on 2026-10-03 while building the first working version, under the maintainer's instruction to decide and record rather than ask; the maintainer iterates on them from here. What could not be settled is in [PLAN.md](./PLAN.md#open). Measurements were taken on macOS with Node v26.10.0 and nub v0.9.5; "measured" means a command in this repository or in a scratch directory was run and its output read.

## The module an import returns

The maintainer's decisions of 2026-10-06: the default export is typed as `as const` types it, the file's text is a `?raw` import, and a `.env` file is imported for its effect. On 2026-10-20 the maintainer removed `?raw`.

```ts
import config from "./app.toml";        // the data: { readonly port: 8080; readonly name: "demo" }
import "./.env";                        // process.env.PORT: string, loaded when the module runs
```

- **The default export is typed as `as const` would type it** (the maintainer's choice, replacing the first version's widened default and its `literal` export). A readonly array or tuple is not assignable to a mutable one: `const tags: string[] = config.tags` fails with `TS4104: The type 'readonly ["a", "b"]' is 'readonly' and cannot be assigned to the mutable type 'string[]'` (measured on `lab/basic`, which keeps that line under `@ts-expect-error`). Plain `.json`, which stays TypeScript's, is still widened by `resolveJsonModule`.
- **No `?raw`,** removed by the maintainer on 2026-10-20: "I'm not sure this is worth including right now. We shouldn't document it. And we should probably just remove it. We'll see if anyone asks about it later." From 2026-10-06 it gave the file's text, the meaning of Vite's `?raw`, served by the preload's hook and the esbuild plugin (esbuild's `text` loader) and typed by ambient declarations, `declare module "*.toml?raw"` and one per extension, in a `client.d.ts` that a project listed in tsconfig's `types` as `motherload/client`. TypeScript resolves no query to a file (below), so the mapper never saw these imports, and every project carried a `types` entry for them. Measured that day on 7.1.0-dev.20261002.1 before it went: a mapper that starts each module it writes with a `/// <reference path>` to its own `client.d.ts` typed `?raw` with no `types` entry, except for a file imported only with `?raw` and outside `include`, which no mapped module brings into the program (`TS2307`); `/// <reference types="motherload/client" />` in its place failed with `TS2688` in a data file outside the project's `node_modules`. A query or hash on a data file's import now goes to the next hook or plugin.
- **No top-level keys as named exports.** Node's JSON modules export only `default`, and a key such as `my-key` would not be an identifier.
- **A `.md` file's default export is the object `{ md, frontmatter }`,** its body and its frontmatter, each also a named export ([below](#the-txt-and-md-modules)).
- **A `.env` import loads the file into `process.env`;** see "The `.env` module" below.
- **Every module is an ES module,** whatever the nearest package.json says, the maintainer's preference of 2026-10-20: "I definitely have a strong preference for going ESM first here." The mapper reports its module as `.mts`. TypeScript takes a mapped file's format from the extension the mapper reports and the nearest package.json's `type`, as it does a real file's (`GetImpliedNodeFormatForFile` on the virtual file name, in typescript-go's `internal/compiler/filesparser.go`, read on main on 2026-10-20), and the transform's answer has no other field for it (`MappedOutput`: `text`, `extension`, `mappings`, `diagnosticDirectives`). With `.ts`, a data file in a package with no `type` was typed as CommonJS, so an ES module's default import of it was the whole module and `config.port` was `TS2339`, though the preload and the plugins load the file as an ES module. Measured on 7.1.0-dev.20261002.1 with a data file in a package with no `type`: an `.mts` importer under `nodenext` failed with `.ts` and passes with `.mts`; a CommonJS `.ts` or `.cts` importer passes either way under `nodenext` and `node20`, which let CommonJS `require` an ES module, as the Node 24 Motherload needs does; under `node16` and `node18`, which model a Node that cannot, a CommonJS importer gets `TS1479` with `.mts`; `preserve`, and `esnext` with bundler resolution, pass either way; declaration emit names the file `config.d.toml.ts` either way. The other way out, `"type": "module"` in the nearest package.json, is the project's to write. `tests/fixtures/commonjs` checks it.

## How an import chooses

The maintainer's idea was a query on the specifier, as in Vite (`./app.toml?raw`, `?const`). Measured with a probe mapper that reports what it receives, on TypeScript `7.1.0-dev.20260918.1` and `7.1.0-dev.20261002.1`:

| Mechanism | TypeScript | What the mapper sees |
| --- | --- | --- |
| Query, `import x from "./y.toml?raw"` | `TS2307: Cannot find module './y.toml?raw'` on both builds | Nothing; no transform |
| Hash, `"./y.toml#raw"` | `TS2307` on both builds | Nothing |
| Import attributes, `with { type: "text" }` or `with { as: "const" }` | Accepted, exit 0 | The transform request carries `fileName`, `content` and `projectHandle` only, so the attribute cannot change the module; one module per file |
| Ambient wildcard, `declare module "*?raw" { const text: string; export default text }` | Accepted; the import is `string` (an `@ts-expect-error` assigning it to `number` is used) | Nothing; the ambient declaration answers, and it cannot see the file, so it cannot type `?const` |
| Named exports (`literal`, `raw`), the first version | Typed per file by the mapper | Everything; the mapper writes all three |

At run time a query does reach the loaders: Node's module hooks resolve `./config.toml?raw` and the template's load hook loaded it (exit 0), and esbuild resolved it to `config.toml`, keeping `?raw` apart in its `suffix`. So a query works everywhere except in the type check, and a design TypeScript cannot type was not shipped.

- **Decided on 2026-10-03: the import chooses by export name** (`literal`, `raw`), the one mechanism the type check, the preload and every bundler agreed on.
- **Revised on 2026-10-06:** with the default typed as `as const`, the one other form left is the text, whose type is `string` whatever the file holds, so an ambient wildcard can type it: `?raw` replaces the `raw` export. A query whose type depends on the file (`?const`, a widened view) still cannot be typed, because the mapper never receives it.
- **Revised on 2026-10-20:** `?raw` is gone (above), so an import has one form, the default export. Read again that day on typescript-go's main branch, where `internal/contentmapper/hostimpl.go` last changed on 2026-08-19: the transform request, `TransformParams`, holds `fileName`, `content` and `projectHandle`, and the module resolver (`internal/module/resolver.go`) has no handling for a query, so a mapper transforms each file once and cannot type an import by its query.
- **Rejected: an option per tsconfig entry** (`options: { literal: true }`, or a second entry for a suffix such as `.const.toml`). Both choose per file or per suffix, not per import, and the second makes users rename files.

## TOML dates

- **An offset date-time is a `Date`** (`new Date(...)` in the module, `Date` in both types): it names an instant.
- **A local date-time, local date or local time is its ISO text** (`"1979-05-27"`, `"1979-05-27T07:32:00.000"`, `"07:32:00.000"`), typed `string`: none names an instant, and a `Date` would invent a time zone. The text is smol-toml's `toISOString()`, which adds milliseconds to a time (`tests/formats.test.ts`).
- Temporal (`Temporal.PlainDate` and the rest, which smol-toml can return) was the alternative; it needs Temporal wherever the module runs. It is in [PLAN.md](./PLAN.md#open).

## The YAML parser: yaml

| Candidate | Latest release | Weekly downloads | Spec | Notes |
| --- | --- | --- | --- | --- |
| yaml (eemeli) | 2.9.1, 2026-09-11 | 258 M | YAML 1.1 and 1.2; "passes all of the yaml-test-suite tests" (its README) | No dependencies, 0.69 MB; errors carry a `[start, end]` range |
| js-yaml | 5.4.2, 2026-09-13 | 363 M | YAML 1.2 and 1.1; "passes the entire YAML Test Suite" (its README) | Depends on argparse, 1.57 MB |

Both pass the suite and are maintained. yaml was chosen for its error ranges (a diagnostic underlines the whole offending token) and its document API, with no dependencies. Its behaviour, each checked in `tests/formats.test.ts` or `lab/basic`:

- **YAML 1.2's core schema,** the library's default, so `yes` is the string `"yes"`.
- **Merge keys (`<<`) are read** (`merge: true`), so a file can share a block of settings between sections (`lab/basic/app.yaml`).
- **A duplicate key is an error,** the library's default.
- **Several documents (`---`) are the list of their values,** in order, typed as a readonly tuple of them; one document is its value; a file with no document is `null`. Refusing a multi-document file was the alternative; it would make a whole class of files unimportable. A single document whose value is a list reads the same as several documents; a `documents` export would tell them apart, and the maintainer kept the one shape on 2026-10-06, because each import is typed exactly from its file, so its author sees the shape it has.
- A YAML value no module can carry (`!!binary`, `!!set`, a Map with object keys under YAML 1.1) is a diagnostic naming its path.

The json5 package, 2.2.3 (2022-12-31, 284 M weekly downloads, no dependencies), is published by the JSON5 project itself (github.com/json5/json5); no other JSON5 parser was found worth weighing. Its `SyntaxError` carries `lineNumber` and `columnNumber`. It keeps a `__proto__` key as a property (measured).

## The `.env` module

The maintainer's decision of 2026-10-06: a `.env` file is imported for its effect, `import "./.env"`, which sets its variables on `process.env` and types them there; no value is baked into a module or a bundle.

- **Types:** the module declares each key on `NodeJS.ProcessEnv` in a `declare global` block, typed `string`. A side-effect import puts the module in the program, so the declaration applies to the whole project: measured on `lab/basic`, `process.env.GREETING` is `string` with the import and `string | undefined` without it.
- **Run time:** the module calls `process.loadEnvFile`, Node's own reader, so the type check and the run read one grammar: the keys come from `util.parseEnv`, which replaced dotenv (dotenv 18.0.5 and `util.parseEnv` gave the same values on sixteen lines covering plain, quoted, `export`, comments and multi-line values, measured on 2026-10-03). A variable the environment already sets keeps its value (measured: `PORT=9999` in the environment stayed `9999` after loading a file with `PORT=3000`).
- **Which file:** under the preload the module's own URL is the file. In a bundle the module is inlined, so it reads the file's path relative to the working directory at build time, from the working directory when it runs; a missing file (`ENOENT`) loads nothing, as a deploy that sets its variables another way has none. `tests/lab.test.ts` checks that the esbuild bundle of `lab/basic` holds no value from its `.env` and prints one when run beside it.
- **No expansion:** `${A}` stays the text `${A}`, as `process.loadEnvFile` leaves it. nub expands `${VAR}` when it loads `.env` (nub's documentation); whether Motherload should is in [PLAN.md](./PLAN.md#open).
- **File names:** a `.env` entry in tsconfig matches a file named `.env` (measured: TypeScript transformed `./.env` for a probe mapper claiming `.env`) and, by the suffix rule, `prod.env`. `.env.local` ends in `.local`, which no `.env` entry reaches; the loaders recognise `.env.*` names if an entry claims their suffix.

## The `.csv` and `.tsv` module

Decided on 2026-10-06, with the four formats below:

```ts
import users from "./users.csv";   // readonly { readonly name: string; readonly email: string; readonly zip: string }[]
```

- **The first row is the header; each later row is an object keyed by it,** and the default export is the array of rows.
- **Every value is a string.** CSV has no types, and guessing numbers corrupts values such as the zip code `02134` (`lab/basic/users.csv` keeps its zero).
- **The type is the column set, not each cell's literal:** a file of thousands of rows would otherwise be thousands of literal types in the checker and in every hover. A column name is a bare property name when it is an identifier and quoted otherwise, as `propertyName` writes one.
- **A file with only a header** is `[]`, typed as its columns' array. **A file with no header** (empty, or only blank lines) is `[]` typed `readonly never[]`: it has no columns, and `never` says no row exists, where `readonly {}[]` would claim rows with no keys.
- **A blank line is not a row,** wherever it is, as Python's `csv.DictReader` skips blank rows (measured: `a,b\n1,2\n\n3,4\n\n` gave two rows). So in a file of one column a blank line is not an empty value; a line holding `""` is.
- **Problems:** a row whose field count differs from the header's is a problem at that row, every such row reported; an empty or repeated column name is a problem at the header; a quoting error is a problem at its row.
- **CSV follows RFC 4180:** quoted fields, doubled quotes, line breaks inside quotes, and spaces kept as part of a field ("Spaces are considered part of a field and should not be ignored", RFC 4180 section 2). Beyond it: LF as well as CRLF, both in one file, and a byte order mark skipped.
- **TSV follows the IANA text/tab-separated-values registration:** a tab between fields and no quoting, so `"` is an ordinary character and `"hi" she said` stays as written. The registration defines no quoting and no escapes: "Each record is represented as a single line", and "fields that contain tabs are not allowable in this encoding". csv-parse, papaparse and d3-dsv all apply CSV quoting to TSV by default (measured with csv-parse: `"x` opening a TSV field was "Quote Not Closed"), which misreads a field that starts with a quote, so Motherload turns it off. The backslash escapes of PostgreSQL's text format (`\t`, `\n`) stay text. Whether spreadsheet exports need CSV quoting in TSV is in [PLAN.md](./PLAN.md#open).

## The `.txt` and `.md` modules

```ts
import notes from "./notes.txt";                  // string
import post from "./post.md";                     // { readonly md: string; readonly frontmatter: { readonly title: "Hello" } }
import { md, frontmatter } from "./post.md";      // each part, as a named export
```

- **A `.txt` file is its text,** typed `string`: a literal type would put the whole file into every hover.
- **A `.md` file's default export is the object `{ md, frontmatter }`,** the maintainer's decision of 2026-10-20: `md` is the body without the frontmatter, typed `string`, and `frontmatter` the frontmatter. It replaced, the same day, a module of the two named exports with no default, which had replaced the first version's default export of the body as a string.
- **The default is there for its hover.** A default import hovers with its whole type, `(alias) const post: { readonly md: string; readonly frontmatter: { … } }`, while TypeScript hovers every namespace import as its name alone: `import * as post from "./post.md"` shows `import post`, as a namespace import of a `.ts` file does (measured with TypeScript 6.0.3's language service, which draws the docs site's hovers). Typing the module as one object with `export =` would give the namespace import that hover, but through the mapper it is `TS1203: Export assignment cannot be used when targeting ECMAScript modules` in the `.md` file, under `nodenext` and under bundler resolution, with or without `skipLibCheck` (measured on 7.1.0-dev.20261002.1).
- **The default's type spells the frontmatter out again,** not as `typeof frontmatter`, which the hover would print as written (measured: `{ readonly md: typeof md; readonly frontmatter: typeof frontmatter }`).
- **`md` and `frontmatter` are also named exports,** so a bundle that imports only `frontmatter` leaves the body out. Measured with esbuild, minified: the body's text was absent from the bundle of `import { frontmatter }` and present in the bundle of the default import.
- **Motherload does not render Markdown:** no Markdown parser is a dependency, and `md` goes to whichever renderer the project uses. Exporting the body rendered as HTML, or as an AST, was left for later by the maintainer ([PLAN.md](./PLAN.md#open)).
- **An `html` export, or an AST, would be made when the module is built, with no renderer in a bundle,** as the two plugins that offer one do (read in their sources on 2026-10-20): Astro's Markdown transform renders the body and writes the HTML into the module as a string, which `compiledContent()` returns, with `getHeadings()` returning a list written in the same way; vite-plugin-markdown renders with markdown-it and exports `html` as a `const`. A bundle that does not import a named export leaves it out, as it leaves out `md` (above), so in a bundle that is the laziness an unused export gets. Rendering when the module runs, on first access, would put a renderer in the module, where every Motherload module today imports nothing. The preload runs the loader in the program's own process, so there each `.md` file would be rendered when it is first imported, used or not. Measured with micromark 4.0.2 and its GFM extension on Node 26.11.1: loading micromark, the extension and mdast-util-from-markdown took 67 ms; rendering took 3 ms for this repository's README (7 KB), 8 ms for the docs page (18 KB) and 26 ms for this file (64 KB); the HTML was about 1.3 times the text, and an mdast as JSON 5 to 7 times the text with positions and about 2 times without.
- **`md` and `frontmatter` are fixed names,** so each is an identifier whatever the file holds (the rule against top-level keys as named exports, above, is about names that come from the file).
- **The frontmatter is a `---` line at the very start of the file, closed by the next `---` line;** trailing spaces on either line, CRLF, and a byte order mark before it are accepted. The body starts after the closing line. A `---` line anywhere else is body (a thematic break).
- **It is read as a `.yaml` file is** (the same function: YAML 1.2's core schema, merge keys, a duplicate key an error) and typed as `as const` would type it. A YAML error is placed at its place in the file, offset by where the frontmatter starts, and yaml's "at line N, column M", which counts from the frontmatter, is dropped from the message.
- **No frontmatter, or an empty one, is `{}`,** typed `{}`; a file with no frontmatter is all `md`.
- **A file whose frontmatter fails to parse** is typed `md: string` and `frontmatter: any`, and its default `{ readonly md: string; readonly frontmatter: any }`, so the problem is the one error and no use of the module adds another; `md` keeps `string` because the body's type does not depend on the file.
- **A frontmatter that is not a mapping** (a list or a scalar) is a problem at the frontmatter: frontmatter is keys and values by convention, and `null` or a list would make every `frontmatter.title` an error.
- **An opening `---` with no closing line is a problem at the opening line,** not a file that is all body: read as body, a forgotten closing line would hide the YAML in the text with no error. A file that starts with a thematic break and has no other `---` line gets the problem; a blank line before the break avoids it.

## The schema loader: types

A `.schema.jsonc` or `.schema.json5` file (`.schema.json` until 2026-10-19, [below](#the-schema-loader-the-suffix)) becomes the type the schema describes plus a validator (the maintainer's decision). The types come from an emitter of Motherload's own, `packages/schema/src/schema-types.ts` (the maintainer's decision of 2026-10-09). The alternatives were json-schema-to-typescript 16.0.0 (2026-08-28, 5.1 M weekly downloads), which compiles a schema to TypeScript declarations but installs 15.9 MB with its dependencies, prettier 9.96 MB of it, loaded every time ([Packaging](#packaging)); and json-schema-to-ts 3.1.1 (47 M weekly downloads, last release 2024-08-29, 0.47 MB with `@babel/runtime` and `ts-algebra`), which infers the type from the schema as a literal type, so the checker computes it again in every type check and each `$ref` is inlined.

- **No dependency:** the emitter is part of Motherload and needs nothing installed; only the validator needs ajv.
- **The root type is always `Type`,** whatever the root `title`, so `import { type Type as User }` works for every schema. An object root is an `interface`, any other root a `type`.
- **Each definition is a named type:** every entry of the root's `$defs` (or draft-07 `definitions`) is exported under its key in PascalCase (`my-tag` is `MyTag`; `Type2` when the name is taken), and a `$ref` to it is that name, so a recursive schema stays finite. `#` is `Type`; a pointer to anything else in the schema is inlined, and is `unknown` when it leads back into itself.
- **The keywords it reads:** `type` (one or a list), `properties` and `required` (an optional property is `a?: T | undefined`; a required key that `properties` does not list has the type of the `patternProperties` whose pattern matches it, or of `additionalProperties` when none does, [below](#the-schema-loader-types)), `additionalProperties`, `patternProperties` and `unevaluatedProperties: false` (an index signature, which also covers the named properties, as TypeScript requires, or none when closed; `unevaluatedProperties` closes the object only when no keyword beside it can allow another key: `allOf`, `anyOf`, `oneOf`, `if`/`then`/`else`, `dependentSchemas` or a `$ref`), `items`, `prefixItems`, `additionalItems` and `minItems` (an array, or a tuple whose positions from `minItems` on are optional), `const` and `enum` (literal types), `allOf` (an intersection), `anyOf` and `oneOf` (a union), `if`/`then`/`else` that test a property's listed values (a union, [below](#the-schema-loader-types)), and `description` (a doc comment). A keyword the schema's draft does not define is not read, `nullable` among them ([below](#the-schema-loader-the-validator)). Without `type`, the object keywords constrain an object and the array keywords an array, and every other JSON value passes them, so the type is that object or array or any other JSON value (`{ "properties": { "a": { "type": "string" } } }` is `{ a?: string | undefined; ... } | unknown[] | string | number | boolean | null`), the maintainer's answer of 2026-10-20: "It should have complete fidelity with what is allowed by the JSON schema itself." Until then such a schema was an object alone, though the validator accepted `5`. The JSON types a value can have come from `type`, `const`, `enum`, `allOf`, `anyOf`, `oneOf` and `$ref`, and a member of `allOf`, `anyOf` or `oneOf`, or a `then` or `else` read as an object, is read within its schema's: `{ "type": "object", "allOf": [{ "properties": ... }] }` is an object and that object, not a union of every JSON type. A schema should declare `"type": "object"` where it means one. A keyword that narrows a value no TypeScript type can express (`minLength`, `pattern`, `format`, `minimum`, `uniqueItems`) leaves the type as it is; `not`, `if`/`then`/`else` of any other shape and the other conditional keywords leave it wider. The validator checks all of them. Arrays and objects are mutable, as json-schema-to-typescript's were, except a `const` or `enum` value, which is typed as `as const` would type it.
- **The rule: the type admits every value the validator accepts.** Each keyword's type is meant to admit every value its rule does, and `allOf`, `anyOf` and `oneOf` compose those types as intersection and union, so a keyword the emitter does not read only widens the type. Checked against ajv on 2026-10-20 for `nullable` (the one keyword found where it did not hold: ajv honours OpenAPI 3.0's `nullable: true` and the type said `string`; the type then added `null`, and since the same day neither reads it, [below](#the-schema-loader-the-validator)), `$async` (ajv made the validator return a promise, which `is` took for a pass; ignored since), `if`/`then`/`else`, `dependentRequired` and `$dynamicRef` (each widens). `unevaluatedProperties: false` beside `allOf` was recorded here as widening too, and did not hold: `{ "type": "object", "allOf": [{ "properties": { "a": { "type": "string" } } }], "unevaluatedProperties": false }` accepted `{ "a": "x" }`, and its type, `{ [key: string]: never } & { a?: string }`, refused it (measured on 2026-10-20 with tsc); since then it closes the object only when nothing beside it can allow a key (above). `tests/schema-types.test.ts` assigns every sample ajv accepts to the type, for these schemas and the conditionals below, and runs tsc. A schema without `type` did not hold either until the same day (above): `{ "properties": { "a": { "type": "string" } }, "required": ["a"] }` accepted `5`, `"x"` and `null`, typed `{ a: string; ... }`, and `"address": { "properties": ... }` accepted `{ "address": 5 }`, typed as an object (measured); the test checks those too. A `$ref` beside other keywords is intersected with them in every draft, as ajv applies them in draft-07 too (measured on 2026-10-20: `{ "$ref": ..., "required": ["y"] }` refused an object without `y` under draft-07), though draft-07's text ignores a `$ref`'s siblings. Three more shapes did not hold, measured on 2026-10-20 and closed the same day, each checked by the same test:
  - **A required key that `properties` does not list,** beside `additionalProperties` or `patternProperties`, was `unknown`, which TypeScript refuses beside a narrower index signature: `{ "type": "object", "required": ["a"], "additionalProperties": { "type": "number" } }` gave `{ a: unknown; [key: string]: number }`, error TS2411 in the mapper's virtual code, so a valid schema failed the type check of every project that imported it. Such a key now has the type of every `patternProperties` entry whose pattern matches it (each applies, so their union admits it), tested as ajv tests a pattern (a Unicode regular expression, unanchored), or of `additionalProperties` when none matches, since a key a pattern matches is not an additional property; `never` when the object is closed and no pattern matches it, as no value then passes, and `unknown` without `additionalProperties`. A pattern this runtime cannot read adds `additionalProperties`' type too.
  - **An optional property was `a?: T`,** which under `exactOptionalPropertyTypes` refuses `{ a: undefined }`, while ajv passes a property that holds `undefined` as absent (it checks `data.a !== undefined`). It is now `a?: T | undefined`, which changes nothing without that option. JSON cannot hold `undefined`, so only a JavaScript value meets it. A required property that holds `undefined` is missing, for ajv and the type alike.
  - **An `$id` below a file's root is refused,** in the type check and the build, as a problem at that `$id`'s value (`embeddedIdProblems` in `packages/schema/src/refs.ts`), or at the root's reference to the file that holds it. ajv resolves a `$ref` inside such a schema against that `$id`, while the emitter resolves every pointer against the file: `{ "$defs": { "x": { "type": "string" }, "inner": { "$id": "https://example.com/inner", "$defs": { "x": { "type": "number" } }, "allOf": [{ "$ref": "#/$defs/x" }] } }, "allOf": [{ "$ref": "#/$defs/inner" }] }` validated `1` and refused `"s"`, typed `string`, in 2020-12 and in draft-07 with `definitions`; with the `$ref` beside the `$id`, ajv recursed until the stack ran out while compiling, reported as an invalid schema. The message names the fix: move that schema to a file of its own and `$ref` the file, or remove the `$id`. A plain-name `$id` (`"#name"`, draft-07's anchor) moves no base and stays, and so do the root's own `$id` and `$id` as data or as a property's name. Standard JSON Schema's conversion refused the same `$id`s already ([below](#the-schema-loader-standard-json-schema)); resolving each `$ref` against its `$id` in the emitter was the alternative.
- **The schema as written is a type of its own, `Json`:** the module declares `type Json = ` the schema's literal type and the default export as `Schema<Type, Json>`, so an error or a hover that names the module prints `Schema<Type, Json>`. With the literal inline it printed the schema itself, truncated (measured on 2026-10-20: `Type 'Schema<Type, { readonly $schema: "https://json-schema.org/draft/2020-12/schema"; readonly type: "object"; readonly properties: { ...; }; ... }>' is not assignable to type 'number'`). `Json` is not exported, since no consumer needs to name it: a library that re-exports a schema module still emits its declarations, TypeScript inlining the literal there (`tests/fixtures/declaration`, `tests/lab.test.ts`). A definition or another file's `Type` imported under that name takes another (`Json2`), as one named `Type` does.
- **Discriminated unions narrow:** a `oneOf` or `anyOf` of objects told apart by a `const` property is a union of object types with that property's literal type, and TypeScript narrows it in an `if` or a `switch`, exhaustively, also when the variants sit beside shared properties (an intersection with the union, which TypeScript distributes). `lab/basic/event.schema.jsonc` is checked that way in `lab/basic/main.ts`. A union written with `if`/`then`/`else` narrows too, since the maintainer's pick of 2026-10-20: when an object schema's `if`, its own or that of each `allOf` member holding only a conditional, tests a required property with `const` or `enum` and nothing else, and that property's schema lists its values (`enum` or `const`, directly or through a `$ref` in the file), the conditionals are a union with one member per listed value, that value with the `then` of each test it passes and the `else` of each it fails. Every value the validator accepts has one of the listed values, so it is in that value's member, and the type stays as wide as the rule needs while TypeScript narrows on the property:

  ```jsonc
  { "type": "object", "properties": { "kind": { "enum": ["click", "visit"] } }, "required": ["kind"],
    "if": { "properties": { "kind": { "const": "click" } } },
    "then": { "properties": { "x": { "type": "number" } }, "required": ["x"] },
    "else": { "properties": { "url": { "type": "string" } }, "required": ["url"] } }
  ```

  is `{ kind: "click" | "visit"; ... } & (({ kind: "click" } & { x: number; ... }) | ({ kind: "visit" } & { url: string; ... }))`. One member per value, rather than each conditional typed as `(if & then) | else`, because an `else` cannot be typed without the complement of its `if`, and without it `(if & then) | unknown` is `unknown`; a chain of N conditionals in `allOf` would also be 2^N intersections for TypeScript to reduce. A property whose values are not listed (`{ "type": "string" }`), one that is not required, an `if` that tests two properties or anything beside `const` and `enum`, and a `$ref` to the values in another file are not read, and widen as before.
- **Compared with json-schema-to-typescript** on 19 schemas on 2026-10-09, by assignability both ways under tsc: the same type for 16. For the other 3, json-schema-to-typescript was wrong: it does not read `prefixItems`, so a 2020-12 tuple became `never[]` and an open one `[boolean, boolean, ...boolean[]]`, and it typed `{}`, which accepts every value, as an object.
- **A `$ref` to another schema file is that file's type,** imported from its module ([below](#the-schema-loader-references-to-other-files)); a `$ref` to a URL is not followed, and its type is `unknown`.
- **The schema itself is checked:** the type check compiles the schema with ajv and reports an invalid one (`tests/fixtures/errors`).

## The schema loader: references to other files

The maintainer's requirement of 2026-10-20: "We absolutely need to follow refs into other files." Built the same day, in `packages/schema/src/refs.ts` with the emitter and the validator.

```jsonc
// team.schema.jsonc, beside user.schema.jsonc and shared/place.schema.jsonc (lab/basic)
{ "properties": { "lead": { "$ref": "./user.schema.jsonc" }, "office": { "$ref": "./shared/place.schema.jsonc#/definitions/place" } } }
```

```ts
// Its module's types, as the mapper writes them:
import type { Type as User } from "./user.schema.jsonc";
import type { Place } from "./shared/place.schema.jsonc";
export interface Type {
  lead?: User;
  office?: Place;
  [key: string]: unknown;
}
```

- **Which file:** a reference's URI part is resolved against the file that holds it, as a relative URL, so `./user.schema.jsonc`, `user.schema.jsonc` and `../user.schema.jsonc` name files near it and a reference in another file resolves against that file. A `$id` does not move it: files are the unit, as TypeScript's imports are. A reference with a scheme of its own (`https:`, `urn:`, `file:`) is a URL and is not followed; ajv reports it, as before. The file must be a `.schema.jsonc` or `.schema.json5` file, so that its module is a schema's.
- **The type is an import of the other file's module,** so TypeScript sends that file through the mapper itself, with no `dynamicConfig` (measured with a probe mapper on 2026-10-20, [PLAN.md](./PLAN.md#content-mapper-facts); `lab/basic/shared/place.schema.jsonc` is reached only this way, and its type is checked exactly in `lab/basic/main.ts`). A pointer to the file's root is its `Type`, imported under a name for the file (`./address.schema.jsonc` is `Address`); a pointer to an entry of its `$defs` or `definitions` is the type its module declares for it, under that name; a name taken in the importing module gets `2`, as a definition's does. A pointer to anything else is inlined from the other file, whose own references are imported in turn. Two files that refer to each other import each other, which TypeScript allows.
- **The importing module's text depends on the other file:** the names it imports and what it inlines. TypeScript transformed every mapped file on every `--incremental` run and on every change under `--watch` (measured on `7.1.0-dev.20261002.1`, [PLAN.md](./PLAN.md#content-mapper-facts)), so the text is never stale on that build.
- **The validator is compiled from every file the schema reaches,** transitively, in one ajv instance: each other file is added with `addSchema` and the root compiled, so a cycle between files validates. The module still imports nothing, and `schema` is the root file's own schema, its references as written.
- **No path in the module:** ajv's standalone code embeds each schema's `$id` (measured: with file URLs as ids, the module held the absolute path four times). Each file is given an id with no path, its own `$id` when that has a scheme and `motherload:<n>` otherwise, and each reference to another of the files is rewritten to that file's id, keyword by keyword (`properties`, `items`, `allOf` and the rest), so data under `const`, `enum`, `default` or `examples` that holds a `$ref` key stays as written (`tests/schema.test.ts` checks that the module holds no part of its directory's path).
- **One draft:** every file is compiled in the root's draft. A file that declares another `$schema` than the root's (drafts 06 and 07 count as one) is a problem; a file that declares none is read in the root's.
- **Problems are placed at the reference** in the root's text: a file that does not exist, cannot be read or does not parse, a file that is not a schema file, a pointer to nothing (`#/$defs/nope`), a draft that differs. A problem in a file the root reaches through another is placed at the root's reference to that file, its message prefixed with the file (`./via.schema.jsonc: The $ref ...`). The reference's type is `unknown`, so the problem is the one error. A referenced file's own problems are also reported in that file, which the import brings into the program (`tests/fixtures/errors/broken-ref.schema.jsonc` is reported at line 4, column 35).
- **Bundlers rebuild on a change to a referenced file:** the loader's `load` returns the files it read as `watchFiles`, which the esbuild plugin passes on, also when the module fails, so creating a missing file rebuilds it (`tests/adapters.test.ts`). The esbuild bundle of `lab/basic` counts `team.schema.jsonc` as one input: the files it refers to are compiled into its validator. The Node and Bun preloads build each module once and watch nothing.
- **Nothing is shared or cached between modules,** the maintainer's question of 2026-10-20 ("if there's a bunch of imported schemas that all reference some shared schema"): each module reads, parses and compiles every file it reaches, and carries its own compiled copy of them. Measured that day with ten schemas that each refer twice to one shared schema of six properties (`pattern`, `email`, `date-time`), against one: a module built in 7 ms once ajv was loaded (40 ms for the first, which loads it), `tsc` took 377 ms against 315 ms, and the esbuild bundle was 188 KB minified (6.3 KB gzipped) against 18.8 KB (3.8 KB), growing with each schema. So caching the compile by path would save milliseconds, and was not added; the size is the cost. Of a module's bytes, a schema of `type: "string"` alone is 1.3 KB minified, and a `format` ajv-formats checks with a function (`date-time`) adds 7.4 KB, because ajv's standalone code requires ajv-formats' whole formats module, which is inlined whole (a regular-expression format such as `email` adds 0.3 KB). Sharing would mean modules that import the modules of the files they refer to and call their validators, which ajv's standalone code cannot link ([PLAN.md](./PLAN.md#open)).

## The schema loader: the suffix

A schema file's suffix is `.schema.jsonc` or `.schema.json5`, and the suffix names the dialect the file is read in (the maintainer's decisions of 2026-10-20: `.schema.jsonc` in the morning, then `.schema.json5` beside it, "I think we can continue supporting it for .schema.jsonc and .schema.json5. Kind of nice to be able to have comments as well."). It was `.schema.json` until 2026-10-19, then `.jsonschema` for a day (the maintainer's answer of 2026-10-19, replaced on 2026-10-20). [microsoft/TypeScript#64581](https://github.com/microsoft/TypeScript/pull/64581), merged 2026-10-13, refuses a content mapper extension that ends in a built-in one with the TS18066 that `.json` itself gets, and the `release-7.1` branch, cut as `7.1.0-beta` on 2026-10-16, carries it. Measured on 2026-10-19 with a tsconfig registering `.schema.json`, `.sql` and `.pg.sql` for a probe mapper: `7.1.0-dev.20260929.1` accepted all three, and `7.1.0-dev.20261019.1` reported `TS18066: Content mapper file extension '.schema.json' is a built-in extension and cannot be registered by a content mapper` and accepted the other two. The pinned `7.1.0-dev.20261002.1` predates the rule.

- **What the rule reserves:** the pattern `/\.(?:[cm]?[jt]s|[jt]sx|json)$/i` (`packages/typescript/src/vscode/extensionApi.ts` in the PR, whose test lists `.ts`, `.tsx`, `.mts`, `.cts`, `.js`, `.jsx`, `.mjs`, `.cjs`, `.json` and `.d.ts` and its kin), so `.jsonc` and `.json5` are not built-in and neither schema suffix ends in one. The PR's subject is the output extensions of a mapped file that another tool emits to disk, not JSON. Measured on 2026-10-20 on the released `7.1.0-beta` (on npm since that day, installed with nub's `--minimum-release-age=0` on the maintainer's word): the four projects of `nub run typecheck` pass, `lab/basic` registering both schema suffixes; `tests/fixtures/errors` gives the same diagnostics as on the pinned build, `broken.schema.json5(3,44)` among them; and an entry registering `.schema.json` and `.schema.json5` gets TS18066 for the first alone.
- **The suffix names the dialect:** `parseSchemaFile` in `packages/schema/src/schema.ts` reads a `.schema.jsonc` file as JSONC (comments and trailing commas), with the parser of the `.jsonc` loader, and a `.schema.json5` file as JSON5 (also unquoted keys, single quotes, hex numbers, `Infinity`), with the parser of the `.json5` loader, each placing its syntax errors. The same text under the other suffix is a syntax error, so a file reads one way wherever it is opened (`tests/schema.test.ts`; `tests/fixtures/errors/broken.schema.json5` is reported at its line and column). Both give the same module.
- **The docs show `.schema.jsonc`, and `.schema.json5` in one line** (the maintainer, later on 2026-10-20: "the docs should only document .schema.jsonc", then "You should document that json5 is supported, but do it in a one-liner in a callout or something."): the README and the docs page document `.schema.jsonc`, and their setup's extension list ends at it; a note at the end of each one's `.schema.jsonc` section (a `<Callout>` on the page, a `[!NOTE]` in the README) says that a schema can be a `.schema.json5` file, which a project adds to its `extensions` list itself. `lab/basic` and the tests keep covering it.
- **Editors:** VS Code's `jsonc` language lists `.jsonc` (`extensions/json/package.json` in microsoft/vscode), and its JSON language service runs on `json` and `jsonc` documents (`extensions/json-language-features/client/src/languageParticipants.ts`); a file names its own schema with `$schema` (VS Code's `docs/languages/json.md`), so a `.schema.jsonc` file whose `$schema` names a draft is checked and completed against that draft. VS Code's built-in mapping of `*.schema.json` to draft-07 (`jsonValidation` in `extensions/json-language-features/package.json`) does not reach `.schema.jsonc`. VS Code lists no JSON5 language, so a `.schema.json5` file gets highlighting from an extension and no schema checking. On GitHub, Linguist (`lib/linguist/languages.yml`) lists `.jsonc` under JSON with Comments and `.json5` under JSON5, so both are highlighted.
- **The alternatives:** `.jsonschema`, one word and the format's name, which no VS Code language and no Linguist language lists, so it is plain text on GitHub and in an editor without `"files.associations"`, and VS Code's JSON service never runs on it; the one thing it would guard against, TypeScript later reserving `.jsonc` or `.json5`, no rule does today, and such a rule would also take the `.jsonc` and `.json5` data loaders. Also: asking the TypeScript team to exempt `.schema.json`, which is unlikely, since the rule extends the ban on built-in extensions rather than standing apart from it, and keeping `.schema.json` until the next TypeScript bump, which it would not survive.
- **Not by content:** a `.jsonc` or `.json5` file is a schema by its suffix alone, the maintainer's answer of 2026-10-21 ("By the suffix alone, as now") to whether a file with a `$schema`, or one whose `$schema` names a json-schema.org draft, should become a schema module. In a data file `$schema` names the schema the file follows: measured that day over the 43 `.jsonc` and `.json5` files outside `node_modules` in the maintainer's projects, 17 had a `$schema`; the 9 that named a draft were Motherload's own `.schema.jsonc` files, and the other 8 were configs naming the schema they follow (five `biome.jsonc`, a `wrangler.jsonc` with `"$schema": "node_modules/wrangler/config-schema.json"`, an `opencode.jsonc`, a `config.jsonc`), each of which would have become a validator. Reading a draft `$schema` alone would leave a schema without `$schema` as data, make an import's type turn on one string inside the file, and make `@motherload/jsonc` and `@motherload/json5` either depend on ajv or read such a file otherwise than `motherload` does.
- **Beside `.jsonc` and `.json5`:** the longest suffix wins in TypeScript, and `formatOf` tests both schema suffixes before `.json5` and `.jsonc`, so a schema reaches the schema loader and any other `.jsonc` or `.json5` file the data loader (`tests/formats.test.ts`); `lab/basic` registers all four in one tsconfig entry.
- **Without Motherload's loader, a runtime reads a schema as data or refuses it.** Measured on 2026-10-20 with `import user from "./user.schema.jsonc"` in `lab/basic`: Node with no loader stops with `ERR_UNKNOWN_FILE_EXTENSION`; nub 0.9.6 and Bun 1.4.3 with no loader load the file as JSONC data, so the default export is the schema object, with no validator on it, though the type check says it is a validator. Measured later that day with `import point from "./point.schema.json5"`: Node 26.11.1 and nub 0.9.6 stop with `ERR_UNKNOWN_FILE_EXTENSION`, and nub did the same in that run for `./user.schema.jsonc` and `./data.json5`, inside the repository and outside it; Bun 1.4.3 loads the file as JSON5 data, with no validator on it. With `motherload/register` (Node and nub through `--import`, Bun through `--preload`) every runtime gave the validator module for both suffixes. A project that imports a schema must register Motherload's loader in every runtime it runs under, which it does for the other formats already.
- **Vite:** on Vite's main branch, read on 2026-10-20 and not run, the JSON transform is rolldown's native `builtin:vite-json` (`crates/rolldown_plugin_vite_json` in rolldown/rolldown), which takes only ids that end in `.json` or `.json?`, so neither schema suffix meets it. The pattern `\.(?:json|json5)(?:$|\?)` is still Vite's `isJSONRequest` (`packages/vite/src/node/plugins/json.ts`): in a module runner's SSR transform with `json.stringify: true` and `namedExports` off (`server/transformRequest.ts`), it sends a matching id's code through `ssrTransformJSON`, which replaces the first `export default` with an assignment in place of transforming the module. That reaches a `.schema.json5` file as it does a `.json5` one, and not a `.schema.jsonc` file ([PLAN.md](./PLAN.md#open)).

## The schema loader: the validator

```ts
import user, { type Type as User } from "./user.schema.jsonc";
user.validate(input);           // { value: input }, or { issues } with every issue; never throws
user.is(input);                 // input is User, stopping at the first failure
user["~standard"].validate(x);  // Standard Schema v1: the same function as validate
user["~standard"].jsonSchema;   // Standard JSON Schema v1, below
user.schema;                    // the JSON Schema, typed as a literal
```

- **`validate` and `is`, and nothing that throws,** the maintainer's decision of 2026-10-20: "We should not provide any method that throws an error. Does AJV not let you produce a complete array of issues, or does it? In my opinion, there should be a `validate` method that returns complete error information, and then the `is` method can return at the first failure and give you back a boolean and/or act as a type guard. Why don't you write all this up as a TypeScript interface?" The interface was written, and the answer was "Build it as written". `validate(value)` returns Standard Schema's result with Motherload's issues, `SchemaResult<T>`: `{ value }`, the value it was given, the same object, or `{ issues }`, every issue, typed as a tuple of at least one; `~standard.validate` is the same function (`user.validate === user["~standard"].validate`), so a Standard Schema library gets the same issues. `is(value)` is a type guard. `schema` is the schema as written, its `$ref`s to other files and the keywords Motherload ignores (`nullable`, `$async`) included, so the docs send a tool that wants the schema to `~standard.jsonSchema.input({ target })`, which is self-contained and leaves those keywords out. Nothing on the module throws but `~standard.jsonSchema` for a target it cannot produce, which Standard JSON Schema requires ([below](#the-schema-loader-standard-json-schema)); where ajv itself throws, both methods answer instead (below). `@motherload/schema` and `motherload` export `SchemaResult` and `SchemaIssue` beside `Schema`. In the type, `~standard`'s own `validate` comes first in the intersection with Standard Schema's props, so that `user["~standard"].validate(x)` is typed `SchemaResult<T>`: with Standard Schema's first, the call took its signature, a result or a promise of one (measured with tsc on 2026-10-20). The alternatives: `parse`, the module's method until that day, which returned the value or threw a `TypeError` carrying the issues (a `SchemaError` in the types), and which the maintainer's rule takes out because it throws; and one validator for both methods, with `allErrors`, which is smaller, but `is` would go on checking a value it already knows fails, where the maintainer asked that it "return at the first failure".
- **Two validators in one module:** ajv sets `allErrors` per instance, so the module is built with two, one with `allErrors` for `validate` and one without for `is`, each compiled from the same files with the same formats, meta-schemas and ignored keywords (`loadAjv` and `compile` in `packages/schema/src/schema.ts`, run once for each). Their standalone codes are inlined into one module that shares one table of run-time modules, so a helper both require (ajv's `ucs2length`, fast-deep-equal, ajv-formats' formats) is in it once (`tests/schema.test.ts`). `is` is the second: on an object whose first property fails, it returns without reading the next one, which `validate` reads (a getter that counts, in the test). What the second costs, measured on 2026-10-20: `lab/basic/user.schema.jsonc`'s module grew from 8,544 to 14,573 bytes (2,601 to 3,402 gzipped), and `lab/basic/event.schema.jsonc`'s, which carries ajv-formats' formats, from 21,916 to 29,985 (5,582 to 6,518 gzipped). `tests/json-schema.test.ts` checks that the two agree on every value it tries, and `tests/verdicts.test.ts` on generated values (JSON's kinds, empty and nested-empty arrays and objects, the schema's own literals, objects of the property names it mentions) for every schema in the labs and the fixtures and a list of its own.
- **`is` confirms a pass where ajv's first-failure code is wrong** (the maintainer, 2026-10-20: "Do option B, but this is something that we should make a note of for when we eventually vendor AJV"). ajv 8.20.0's validator without `allErrors` accepts `[]` for `contains` beside a tuple, which the schema refuses and the validator with `allErrors` refuses: `{ "prefixItems": [{ "type": "string" }], "contains": { "type": "number" } }` in 2020-12, a draft-07 list of `items` with `contains`, and either nested in a property (measured; draft-07's `prefixItems`, which draft-07 ignores, does not). The cause, read in the code ajv generates: `prefixItems` sets the validity it gates the next keyword on only inside `if (len0 > 0)`, so for an empty array it stays `undefined` and `contains` never runs; with `allErrors` the keywords are not gated on each other. Not reported to ajv (its issues and pull requests searched on 2026-10-20; the nearest, ajv-validator/ajv#502, is a 2017 ajv 5 bug, fixed), and 8.20.0 is its latest release. So when the build finds `contains` beside `prefixItems` or a list of `items` in any file the validator is compiled from (`needsConfirmation` in `packages/schema/src/schema.ts`), the module's `__confirm` is `true` and `is` checks a pass again with `validate`'s validator; otherwise `is` is the first validator alone. The alternative was one validator for both, which costs every `is` the full check; the guard goes when the validator is Motherload's own ([PLAN.md](./PLAN.md#open)).
- **An issue** (`SchemaIssue`) is `{ message, path, keyword }`: ajv's `message`, the `path` in the value and the `keyword` that failed. The maintainer's answer of 2026-10-20 on ajv's `params` and `schemaPath`, which it carried until then: "Drop both". `schemaPath` pointed at the wrong place across `$ref`s and files: it is relative to the compiled function that raised the error, so an error in a recursive `$defs/node` read `#/properties/name/type`, which is not at the root, and one in another file read as an internal id (`motherload:1/properties/name/type`) or as the root's own (measured in the review of the interface). And anything an issue carries, a validator of Motherload's own would have to reproduce, while a field can be added later without breaking anyone. The path holds object keys as strings and array indexes as numbers. ajv's `instancePath` is a JSON Pointer, which writes an index as it writes a key (`/0` either way), so each unescaped segment is read against the value it names: under an array a number, under anything else a string, so `{ "map": { "0": 1 } }` gives `["map", "0"]` and `{ "list": [1] }` gives `["list", 0]`. Reading the value again runs a getter once more (ajv reads a property twice, so the walk is its third read); a read that throws then leaves the rest of the pointer as keys, rather than making `validate` throw.

## The schema loader: Standard JSON Schema

The schema module implements Standard JSON Schema v1 (`@standard-schema/spec` 1.1.0, 2025-12-15) for the `"draft-07"` and `"draft-2020-12"` targets, the two the spec "strongly recommends" (the maintainer's answer of 2026-10-20: "Yes, draft-07 and 2020-12"). A library that needs a schema as JSON Schema (an API or tool definition) reads it from `~standard.jsonSchema`:

```ts
user["~standard"].jsonSchema.input({ target: "draft-2020-12" }); // { $schema: "https://json-schema.org/draft/2020-12/schema", ... }
user["~standard"].jsonSchema.output({ target: "draft-07" });     // the same schema as input: nothing transforms the value
user["~standard"].jsonSchema.input({ target: "openapi-3.0" });   // throws, as the spec asks of a target the library does not support
```

- **Computed when the module is built** (`packages/schema/src/json-schema.ts`, called from `schemaCode`): the module carries each target's schema, or the reason it has none, and returns a fresh copy (`structuredClone`) on each call, so a caller may change it. `input` and `output` are the same, since validation never changes the value.
- **Self-contained:** every other file the schema reaches through a `$ref` is folded in under the target's container (`$defs` in 2020-12, `definitions` in draft-07), keyed by its name without the suffix (`user`, `user2` when taken), and every `$ref` becomes a JSON Pointer into the one document: `lab/basic/team.schema.jsonc`'s `lead` is `#/$defs/user` in 2020-12 and `#/definitions/user` in draft-07. A folded file loses its `$schema` and `$id`; a reference to a file's absolute `$id` becomes a pointer too; a URL `$ref` is left as written. This is not 2020-12's bundling (core 9.3.1), which keeps each file's `$id` and its references as written: the verdicts are the same, and the schema paths of errors differ.
- **Converted where the two drafts say the same thing:** `definitions` and `$defs`; a list of `items` with `additionalItems` and `prefixItems` with `items`; `dependencies` and `dependentRequired`/`dependentSchemas` (a property in both is `{ allOf: [{ required }, schema] }` in draft-07); a draft-07 `$id: "#name"` and `$anchor`, every reference to an anchor becoming a pointer. Draft-07 ignores the keywords beside a `$ref` (core 8.3) while ajv and the later drafts apply them, so going to draft-07 a `$ref` with validating keywords beside it moves into `allOf`. A keyword the schema's own draft does not define (`prefixItems` in a draft-07 schema, which ajv ignored) is left out of both targets, so the target does not start applying it; a vendor keyword (`x-foo`) is kept.
- **Refused rather than approximated:** where a keyword has no exact equivalent in the target, that target throws with the keyword and its place (`./file#/pointer`), and the other target still converts. To draft-07: `unevaluatedProperties`, `unevaluatedItems`, `minContains`/`maxContains` beside `contains`, `$dynamicRef`/`$dynamicAnchor`, `$recursiveRef`/`$recursiveAnchor`. From 2019-09 to 2020-12: `$recursiveRef`/`$recursiveAnchor`, and `unevaluatedItems` in a schema that uses `contains`, which 2020-12 counts as evaluating items and 2019-09 does not (2020-12 core 11.2). In 2020-12, `$dynamicRef`/`$dynamicAnchor` across several files, whose resolution one document does not keep apart. In both: an `$id` inside a file (which the module refuses before the conversion, [types](#the-schema-loader-types)), a root `$id` with a fragment, a `$ref` to something that is not a schema the conversion places, and one name in both `definitions` and `$defs`.
- **Checked by equivalence** (`tests/json-schema.test.ts`): for each produced schema, ajv compiling it for its target (`ajv` or `ajv/dist/2020`, with `allErrors`, ajv-formats and `strictSchema`, so a keyword the target would ignore fails the compile) gives the same verdict as the module's own validator on valid and invalid values, for the fixtures in `tests/fixtures/json-schema/` (2020-12, draft-07 and 2019-09, across files, with anchors, tuples and both kinds of dependency) and for `lab/basic`'s schemas; `lab/basic` prints `team`'s two conversions under the preload and from the esbuild bundle.
- **Not verified:** equivalence is measured with ajv alone, so that a draft-07 reader ignores a `$ref`'s siblings is covered by the shape of the output, not by a second validator; `format` is carried as written, which ajv-formats asserts in both drafts and a default 2020-12 validator treats as an annotation.

## Values a module carries

The serializer (`packages/core/src/serialize.ts`) writes each parsed value as JavaScript and as two type texts. Beyond JSON: `NaN`, `Infinity`, `-Infinity` and `-0` (YAML `.inf`, JSON5 `Infinity`, TOML `nan`), `bigint` (`123n`), and `Date`. A `"__proto__"` key is written as a computed key, because `{"__proto__": x}` in an object literal sets the prototype (`tests/serialize.test.ts`). Literal types: `NaN` and the infinities are `number`, as TypeScript has no literal type for them. Anything else (a Map, a Set, bytes, `undefined`) is a diagnostic naming its path.

## Diagnostics

- **Positions are UTF-8 bytes.** The mapper declares `positionEncoding: "utf-8"` in `initialize`, as the template and dotsql's mapper do, and dotsql's mapper places its diagnostics in UTF-8 bytes; the parsers report UTF-16 offsets, so the mapper converts them (`utf8Range`). The template passed UTF-16 offsets through, which places an error after a non-ASCII character too early. Measured: `tests/fixtures/errors/broken.toml`, whose first line holds `é`, reports `broken.toml(2,8)`.
- **Codes** (shown as `motherload<code>`): 1 syntax, 2 a value no module can carry, 3 a file whose suffix Motherload does not read, 4 the schema, 5 an option in tsconfig.
- **A file that does not parse is typed `any`.** The diagnostic in the file fails the type check already; `any` keeps every use of the import from adding errors of its own. The template typed it `never`, and dotsql types a failed analysis `unknown`.

## The mapper process

- **No `dynamicConfig`.** A data file's module depends on the file alone, and a schema's on the file and ajv. A `$ref` to another file keeps the flag off: the types import that file's module, which TypeScript follows itself ([above](#the-schema-loader-references-to-other-files)). Without the flag TypeScript computes the transform identity from the package name and version and the tsconfig options without starting the process (the content mapper PR's text, quoted in the porg repository's `docs/prior-art.md` section 4b), and starts it only for a matching file. Measured with probe mappers on both builds: a static mapper with no matching file in the program started no process, with or without `--incremental`, while a `dynamicConfig` mapper started and answered `openProject` on every `--incremental` run, with no matching file present.
- **No options.** A key in a tsconfig entry's `options` is reported (code 5) through `optionDiagnostics`, the field dotsql's mapper uses.
- **One tsconfig entry for every format.** TypeScript starts one process per package and version (measured: two entries of one package, one process, each entry its own `openProject` with its own `options`). The failure budget is per entry (below), so a project that wants one format's failures kept apart from the others' lists that format in an entry of its own.
- **Plain `.json` stays TypeScript's:** a mapper cannot claim it (`TS100021` on `7.1.0-dev.20260918.1`, `TS18066` on `7.1.0-dev.20261002.1`: "a built-in extension and cannot be registered"), and `.schema.json` could be claimed beside it on both builds (measured: the probe mapper transformed `user.schema.json` while `plain.json` was typed by `resolveJsonModule`). From the nightly after 2026-10-13 no suffix that ends in `.json` can be claimed either, which is why a schema is a `.schema.jsonc` or `.schema.json5` file ([above](#the-schema-loader-the-suffix)).

## The TypeScript build

The repository pins `typescript@7.1.0-dev.20261002.1`, the newest nightly older than nub's 24-hour minimum release age on 2026-10-03 (`7.1.0-dev.20261003.1` was refused with `ERR_NUB_NO_MATURE_MATCHING_VERSION`). dotsql uses `7.1.0-dev.20260918.1`. Every probe below ran on both, with the same behaviour; the content mapper diagnostic codes were renumbered between them:

| Diagnostic | 20260918.1 | 20261002.1 |
| --- | --- | --- |
| A built-in extension (`.json`) | TS100021 | TS18066 |
| An extension in two mappers | TS100022 | TS18067 |
| Mappers without `--runExternalCode` | TS100024 | TS18068 |
| A failed transform | TS100025 | TS18069 |
| A mapper switched off after five failures | TS100026 | TS18070 |

A later rule is on neither build: from the nightly after 2026-10-13, an extension that ends in a built-in one, such as `.schema.json`, is refused with TS18066 (measured on `7.1.0-dev.20261019.1` and on the released `7.1.0-beta`, [above](#the-schema-loader-the-suffix)).

Failure budget, measured with a mapper that throws for files named `fail*`: one entry, seven failing files: seven transform requests, five failed-transform diagnostics, then the switched-off diagnostic. Two entries of one package, four failing files each: eight failed-transform diagnostics, none switched off. One entry claiming both extensions, the same eight files: five, then switched off. So the budget of five counts per tsconfig entry, not per package or process.

## The starting point: the loader template

The sources started from the loader template in [lab/universal](./lab/universal) (the maintainer's decision: the template stays a template, not a published package), whose contract and adapters are `packages/core/src/universal.ts` and whose JSON-RPC server is `packages/core/src/rpc.ts`, unchanged. Changes from the template:

- **Two functions instead of one `load`:** `load` (synchronous JavaScript for the preload and bundlers, since Node's `registerHooks` is synchronous) and `types` (TypeScript for the checker, which may be asynchronous, since only the mapper calls it).
- **A RegExp `filter` instead of `extensions` and `test`:** the loaders match `.env` files by name, which an extension list cannot express; Bun and esbuild take a RegExp, and the pattern avoids lookaround for esbuild's RE2.
- **UTF-8 diagnostic positions** and **option diagnostics** in the mapper adapter.
- **An `.mts` module, not `.ts`,** above.
- **A query or hash is left to the next hook,** above.
- **Problems instead of a thrown error inside `load`,** so one type serves both texts.

## Packaging

Decided by the maintainer on 2026-10-08 and 2026-10-09: Motherload becomes a family of packages released together at one version. Each format is a package of its own under the `@motherload` scope, complete with its mapper, preload, esbuild plugin and parser; `motherload` is the package of all of them, with one mapper, one preload and one plugin; the code they share is `@motherload/core`, a published dependency of every other package. Built on 2026-10-20, the maintainer's answer that day: "Build them, then document them in Setup" (the docs page's "One format at a time").

| Package | Extensions | Dependencies, each at an exact version |
| --- | --- | --- |
| `@motherload/core` | none: the loader contract and its adapters (Node hooks, Bun, esbuild, the mapper's handlers), the JSON-RPC server, the serializer, the error codes and positions | none |
| `@motherload/toml` | `.toml` | core, smol-toml |
| `@motherload/yaml` | `.yaml`, `.yml` | core, yaml |
| `@motherload/json5` | `.json5` | core, json5 |
| `@motherload/jsonc` | `.jsonc` | core, jsonc-parser |
| `@motherload/env` | `.env` | core (the parser is Node's `util.parseEnv`) |
| `@motherload/csv` | `.csv`, `.tsv` | core, csv-parse |
| `@motherload/txt` | `.txt` | core |
| `@motherload/md` | `.md` | core, `@motherload/yaml`, whose parser reads the frontmatter |
| `@motherload/schema` | `.schema.jsonc`, `.schema.json5` | core, `@motherload/jsonc` and `@motherload/json5`, whose parsers read the two dialects with positions in the schema, ajv, ajv-formats; the types come from Motherload's own emitter |
| `motherload` | all of the above | core and the nine format packages |

A format package's manifest as `nub run build` writes it, `@motherload/yaml` here; `./loader` is the format's `LoaderPlugin`, which `motherload` combines with the other eight:

```jsonc
{
  "name": "@motherload/yaml",
  "type": "module",
  "exports": {
    "./loader": { "types": "./src/loader.d.ts", "default": "./src/loader.js" },
    "./register": { "types": "./src/register.d.ts", "default": "./src/register.js" },
    "./esbuild": { "types": "./src/esbuild.d.ts", "default": "./src/esbuild.js" } // export default function yaml()
  },
  "typescript": { "contentMapper": { "exec": ["node", "src/mapper.js"], "compilerOptions": [] } },
  "dependencies": { "@motherload/core": "0.0.0", "yaml": "2.9.1" }
}
```

`motherload`'s manifest has the same `typescript` field and the `./register` and `./esbuild` exports, over the combined loader, and depends on `@motherload/core` and the nine format packages at the release's version.

| A project's setup | With `motherload` | With `@motherload/yaml` |
| --- | --- | --- |
| tsconfig entry | `{ "package": "motherload", "extensions": [ every extension it uses ] }` | `{ "package": "@motherload/yaml", "extensions": [".yaml", ".yml"] }` |
| Node.js | `--import motherload/register` | `--import @motherload/yaml/register` |
| esbuild | `plugins: [motherload()]` | `plugins: [yaml()]` from `@motherload/yaml/esbuild` |

- **Exact versions throughout,** so the transform identity, which TypeScript computes from the mapper package's name and version and the tsconfig options (the content mapper PR's text, quoted in the porg repository's `docs/prior-art.md` section 4b), changes whenever a parser does. An optional peer's version is outside that identity: an `--incremental` build could keep a module built with an older peer (this follows from the PR's text and was not measured).
- **One owner per extension:** two packages that claim one extension fail the type check (`TS18067`), so a project lists `motherload` or a format package for each extension, never both.
- **One process per package:** TypeScript starts one mapper process per package, so `motherload` serves every format from one process, one tsconfig entry, one `--import` and one plugin; a project of two format packages has two of each.
- **A scoped package is a mapper like any other:** measured on `7.1.0-dev.20261002.1`, a tsconfig entry `{ "package": "@probe/loader" }` started that package's mapper and typed a `.toml` import from it.
- **A project that runs under the preload** loads its Motherload package at run time and lists it in `dependencies`; a bundled project lists it in `devDependencies`, because a generated module imports no package at run time, the validator included. A format package keeps the first case small: an app that preloads only TOML installs `@motherload/core`, `@motherload/toml` and smol-toml.
- **The repository:** `packages/<name>/` holds each package but `motherload`, which is the repository's root, linked into it with `link:` as Reylo links its engines; the root `package.json` also lists every parser, from which the packages' sources resolve them, so one install at the root serves all of them and the docs site's install (the root, then `site/`) is unchanged. A pnpm workspace was the alternative; the links keep the layout Reylo already uses (`@reylosql/postgres: link:packages/postgres` in its root `package.json`). Each manifest in the repository is private and points at its TypeScript sources, so the tests and the labs run without a build.
- **The build:** `nub run build` (`scripts/build.ts`) compiles every package with tsc (`tsconfig.build.json`) into `dist/<dir>`, one directory per package to publish with `npm publish dist/<dir>`: JavaScript, declarations, a README, and a manifest whose exports and mapper name the compiled files (Node strips no types under `node_modules`), with each Motherload dependency at the release's version and every other at the version installed here. `nub run check-dist` (`scripts/check-dist.ts`) packs each into a tarball, installs the tarballs into two projects outside the repository, a copy of `lab/basic` on `motherload` and a copy of `lab/packages` on `@motherload/toml`, `@motherload/jsonc` and `@motherload/schema` alone, and type-checks, preloads and bundles each: passed on 2026-10-20, under nub's isolated layout, where a package reaches only its own dependencies. The format packages' install held core, json5, jsonc, schema, toml, ajv, ajv-formats and smol-toml, and no YAML or CSV parser.
- **The longest suffix, in every host:** TypeScript gives `user.schema.jsonc` to the entry with the longer suffix, `@motherload/schema` over `@motherload/jsonc`. A host does not: Node runs the hook registered last first, and esbuild runs plugins in their order, so the JSONC package's loader would read a schema as data, its validator gone, for one order of the flags. So each loader names its extensions, and of the Motherload loaders in one host, the one claiming the longer suffix of a file loads it: a Node hook passes the file to the next hook, an esbuild plugin returns nothing for it (it sees its siblings in `initialOptions.plugins`), and a Bun plugin, which may not return nothing (oven-sh/bun#5303), loads it with that sibling. Node's and Bun's registrations are process-wide, kept on `globalThis`. `tests/packages.test.ts` checks both orders in each host, and `lab/packages` gives the JSONC package's hook and plugin first. A `.env.<name>` file is claimed by name alone, so a format that reads its suffix wins (`.env.toml` is TOML).
- **One diagnostic source:** every package reports as `motherload` (`motherload1` is a syntax error whichever package found it), and a package's message for an extension it does not read names the package: "@motherload/toml reads .toml files; … Remove its extension from @motherload/toml's contentMappers entry."
- **A schema's types import `Schema` from the package the project installed:** `@motherload/schema`, or `motherload`, whose own types re-export it. A type import in the generated module resolves from the schema's directory, where, under pnpm's layout, only the project's own dependencies are.
- **The `@motherload` scope replaces the per-format `dot<ext>` names,** which stay reserved: `dotyaml`, `dotyml`, `dotjson` and `dotmd` are held by other people ([PLAN.md](./PLAN.md#names)).
- **The schema's validator stays compiled when the module is built** (above), with ajv a dependency of `@motherload/schema`, so `format` is always checked. A run-time ajv was the alternative; measured on 2026-10-09 for one schema (`minLength`, `format: "email"`), bundled and minified with esbuild: 134 KB (41 KB gzipped) with ajv and ajv-formats, which compile the validator with `new Function`, against 4.2 KB (1.6 KB gzipped) for the module Motherload builds, which has no `new Function`. Loading ajv took 21 ms and compiling the schema 15 ms. A Content Security Policy without `unsafe-eval` refuses `new Function`.

Sizes, from the npm registry's `dist.unpackedSize` on 2026-10-07:

| Package | Version | Unpacked size | Needed for |
| --- | --- | --- | --- |
| smol-toml | 1.9.0 | 0.14 MB | `.toml` |
| yaml | 2.9.1 | 0.69 MB | `.yaml`, `.yml`, a `.md` file's frontmatter |
| json5 | 2.2.3 | 0.24 MB | `.json5` |
| jsonc-parser | 3.3.1 | 0.21 MB | `.jsonc` |
| csv-parse | 7.0.3 | 1.61 MB | `.csv`, `.tsv` |
| json-schema-to-typescript (not used) | 16.0.0 | 15.9 MB with its dependencies, of which prettier 3.9.9 is 9.96 MB | a schema's types, before Motherload's own emitter |
| ajv, ajv-formats | 8.20.0, 3.0.1 | 1.03 MB, 0.06 MB | a schema's validator and `format` |
| typescript (for comparison) | 7.1.0-dev.20261002.1 | 3.98 MB, plus 28.7 MB for `@typescript/typescript-darwin-arm64` | the compiler every Motherload project already installs |

A schema's types come from Motherload's own emitter (the maintainer's decision of 2026-10-09, [above](#the-schema-loader-types)), so `motherload` installs about 4 MB. With json-schema-to-typescript it would have installed 18.8 MB, 85 percent of it for a schema's types: prettier cannot be left out, because json-schema-to-typescript's `index.js` requires its formatter, which requires prettier, when it loads. json-schema-to-ts was 0.47 MB with its two dependencies; measured on `7.1.0-dev.20261002.1`, its `FromSchema` gives the exact types but inlines each `$ref` and is computed again in every type check. The parsers cost little to load: before the split, `src/formats.ts` imported all five statically, and importing it took 19 to 47 ms in a fresh Node process (three runs); json-schema-to-typescript took 59 ms and ajv 35 ms.

The shapes that were considered, on 2026-10-07: one package with the parsers as dependencies (the first version); one package with each parser an optional peer, which saves up to 2.88 MB and moves the parser's version outside the transform identity; one package per format with no package of all of them, which gives every project a process per format; and, for `.schema.json`, three optional peers (the first version), one `@motherload/schema` peer, a mapper package of its own, or dependencies of Motherload.

Schemas stay in `motherload`, the maintainer's answer of 2026-10-21 ("Keep it in `motherload`") to whether to take them out before 0.0.1 was published. The two alternatives were `motherload` as the eight data formats with `@motherload/schema` installed beside it (its own tsconfig entry, preload, esbuild plugin and mapper process; the combination already works, `lab/packages`), and a product of its own, as Reylo is for SQL. Measured that day: the schema package was 1,828 of the 2,708 lines of package source and its four test files 1,626 of the 2,306 lines of tests; ajv and ajv-formats were about 1.09 MB of `motherload`'s install; a bundled schema module imports nothing, and under the preload ajv compiles the schema in the project's process (87 files and about 46 ms for one schema, refused under `--disallow-code-generation-from-strings`); and npm held only the 0.0.0 placeholders, so no published version had included schemas.

## Releasing

Every package is released at one version by `.github/workflows/release.yml`, the maintainer's request of 2026-10-20: "We should try to pull in the release infrastructure from Zod and get the first version published", and "We'll need to set up trusted publishing as well." It is Zod's release (`.github/workflows/release.yml` and `.github/scripts/npm-stage-publish.sh` in colinhacks/zod), for eleven packages in place of Zod's two.

- **Dispatch only:** the workflow runs on `gh workflow run release.yml -R colinhacks/motherload` and from `main` alone, never on a push or a tag. A dispatch needs a GitHub session or token with write access, which a stolen push credential is not, the shape of the 2026-09-21 compromise of nubjs/nub, where a pushed tag published 18 packages unattended (Zod's workflow, quoting it). A version bump on `main` publishes nothing by itself.
- **Stage-only trusted publishing:** each package's npm trusted publisher is this workflow in colinhacks/motherload on its `npm` environment, with `--allow-stage-publish` and not `--allow-publish`, so the workflow authenticates with OIDC, holds no npm token, and can only put a version in npm's staged queue, where it is not installable. A version is served once the maintainer approves it with 2FA, with `stager` (`~/Documents/stager`), which approves every staged version under one code and resumes the run.
- **Two GitHub environments:** `npm`, which the staging job runs in, and `release-approval`, a job with no runner that holds the run, for up to 30 days, until the maintainer resumes it; each deploys `main` alone and has the maintainer as its required reviewer, as Zod's have. The npm approval is the gate: the last job waits up to 340 minutes for npm to serve every version, through the automated review npm runs after an approval (16 to 116 minutes for Zod's releases), before it creates the GitHub release `v<version>` at the run's commit, its notes the packages and the commits since the previous tag.
- **What is checked before anything is staged:** `nub run typecheck`, `nub run test`, `nub run build` and `nub run check-dist` in the first job; the staging job builds and runs `check-dist` again, so what it stages is what it checked. `.github/workflows/test.yml` runs the four on every push to `main`.
- **Left out of Zod's:** the JSR publishes, and the scheduled check that zod and @zod/mini are at the same version, which `scripts/build.ts` and `tests/packages.test.ts` already enforce for Motherload's packages.
- **The order:** `@motherload/core` is staged first and `motherload` last, so the staged queue, which `stager` approves oldest first, reads in dependency order.
- **The version:** `nub run bump <version>` (`scripts/bump.ts`) writes it into every manifest and every dependency between them. The first release is 0.0.1, the maintainer's choice of 2026-10-21 ("you should be staging 0.0.1"), over the 0.1.0 first proposed.
- **The first publish:** npm can configure a trusted publisher only for a package that exists (`npm help trust`, "Package must exist", npm 11.20.0), so the workflow cannot make a package's first publish. On 2026-10-20 npm had `motherload` (`0.0.0`, and a `0.0.0-stage` from 2026-10-03) and the `@motherload` organization with no packages (`https://registry.npmjs.org/-/org/motherload/package` answered `{}`). `scripts/npm-first-publish.sh`, run by the maintainer, publishes a `0.0.0` placeholder for each package missing from npm and then configures each trusted publisher, under a browser login of its own that it logs out of when it exits, as nub's `scripts/npm-first-publish-runner.sh` did for nub's runner packages. Its run of 2026-10-21 published the ten `@motherload` placeholders: npm answered each publish with `202` and "Your package is being processed and may take a few minutes to become available", showed a package's one version as `0.0.0-stage`, "Temporary package placeholder for staged publishing", in the meantime, and served `0.0.0` beside it within six minutes, the shape `motherload` has had since 2026-10-03. Its trust commands failed: `npm trust` accepts only its own flags and read `--userconfig <path>` as a stray positional argument, so the login file is passed as `NPM_CONFIG_USERCONFIG` instead, and the first staging run failed with `E401` after npm's token exchange answered "OIDC token exchange error - package not found" (run 39559700934).
