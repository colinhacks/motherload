# Agent notes

Read [PLAN.md](./PLAN.md) first: what Motherload is, what the maintainer decided, the content mapper facts and where each was confirmed, the steps, and what is open. [DESIGN.md](./DESIGN.md) holds one section per design decision with its alternatives and evidence; a change to a decision updates its section.

The Motherload package types data-file imports (`.toml`, `.yaml`/`.yml`, `.jsonc`, `.json5`, `.env`, `.csv`, `.tsv`, `.txt`, `.md`): a TypeScript 7.1 content mapper, a preload and bundler plugins. Its sibling products are dotsql (`~/Documents/projects/dotsql`, the `.sql` loader), dotschema (`~/Documents/dotschema`, the `.schema.jsonc` and `.schema.json5` loader, a type plus a validator, which left Motherload on 2026-10-21) and porg (`~/Documents/projects/lando`, the porg repository: the reactive Postgres driver, `pg_porg` and live queries). Read those repositories; do not write to them.

## Layout

The root `package.json` links `motherload` to the repository root (`link:.`), because a mapper package does not resolve through self-reference, links each `packages/<name>` as `@motherload/<name>`, and links the template's `universal-toml` and `universal-toml-2` the same way. It also lists every package's parser, from which the linked sources resolve them, so one `nub install` at the root serves them all; there is no workspace. Every `package.json` in the repository is private and points at TypeScript sources; only `dist/` is published.

## JavaScript: nub

Prefer `nub` over `node`, `bun`, `npm`, `npx`, `pnpm` and `yarn`: run files with `nub <file>`, package scripts with `nub run <script>`, local CLIs with `nubx <tool>`, installs with `nub install` and `nub add`. The lockfile (`pnpm-lock.yaml`) is respected both ways. Use `nub --node <file>` for strict, unaugmented Node; nub's own loaders for `.toml`, `.yaml`, `.json5` and `.jsonc` are off there, which is what a check of Motherload's preload wants.

- Running `nub run typecheck` type-checks the sources and runs the content mappers on `lab/universal/app`, `lab/basic` and `lab/packages` (`tsc --runExternalCode`).
- Running `nub run build` writes `dist/`, and `nub run check-dist` then installs it outside the repository and runs it.
- Running `nub run test` runs `tests/**/*.test.ts` with `node --test`.
- Running `nub run dev` in `site/` serves the docs site on port 3312; `nub run build` there fails when a page example stops type-checking.
- Setting `TS_CONTENT_MAPPER_DEBUG=1` on `nubx tsc -p lab/basic/tsconfig.json --noEmit --runExternalCode` prints the JSON-RPC traffic.
- The nub installer refuses a package version younger than 24 hours (`minimumReleaseAge`); the TypeScript nightly is pinned to one that passed it. Do not bypass the gate.

## Git

Work lands on `main` directly, with no branch or pull request. When a task is done and `nub run typecheck` and `nub run test` pass, commit it to `main` and push it to `origin` without asking. The push may also carry commits another session left unpushed on `main`; push them with it. Several sessions can work in this checkout at once, so stage only the files the task changed.

A release is never cut by a push: run `nub run bump <version>`, commit and push it, then `gh workflow run release.yml -R colinhacks/motherload`, approve the run's `npm` deployment, and ask the maintainer to approve the release in `stager`, either in a terminal or with its notification's Approve button: each asks for one authenticator code, approves every staged version with it and resumes the run ([DESIGN.md](./DESIGN.md#releasing)). Never use `stager --web` or `stager approve`, whose browser flow asks for a passkey once per package, since the account cannot skip 2FA for five minutes; the notification did the same until stager's 276e7e6. After the approval, `stager --list` should show nothing of the release left: a partial approval leaves a package live with its dependencies still staged, as the first release's did for ten minutes.

## Writing conventions

The product is Motherload, capitalized, in prose and in every message a user reads; `motherload` is the npm package, the import specifier and the diagnostic source, always as code. Its icon is three stacked gold bars, drawn as an SVG (`site/public/icon.svg`, the favicon, and the same drawing in `site/public/motherload.svg`): the site's favicon, the top of its left column, and the README's title. Never hard-wrap Markdown: every paragraph, list item and table row is one line. JSONC comes before JSON5 wherever both appear, in a list, a table, the docs page's sections and an extension list (the maintainer, 2026-10-21: "Be sure to always lead with JSONC. It's way more important than JSON5"). Write a method with its dot and parentheses, `.is()` and `.validate()`, never a bare `is` (the maintainer, 2026-10-21: "Always refer to methods like `.is()` instead of just `is`"). Never open a sentence with inline code (the same day: "Never start a sentence within inline code"): a word that names the thing leads, as in "The `motherload` package is every format together". On the docs page and in the README, show a behavior as an example, a sentence that leads into its own code block, as each format's section under Loaders does, with one fact to each example: a format's first example loads a plain file, and each later one adds a single thing, as `.yaml`'s second shows a file of several documents (the maintainer, 2026-10-21: "Every example needs to be a very clean little chunk containing just new information ... It's just one piece of information at a time, always"); leave out what a reader does not need: an edge case, a rule a parser or TypeScript already enforces, a reason behind a name. Never put three paragraphs in a row (the maintainer, 2026-10-20: "Never, ever have three paragraphs in a row like this. This looks like shit"), and never a list of dense rules with code inline in place of them (2026-10-21, of such a list under the `.schema.jsonc` section the page had then: "not acceptable. It's just not even needed ... Just break up that section into a series of examples with different code blocks ... The vast majority of that does not need to be stated"). A fact the docs leave out stays in DESIGN.md. Never estimate developer time. Anything stated as fact traces to a file read or a command run; a guess goes in PLAN.md's Open section as a question.
