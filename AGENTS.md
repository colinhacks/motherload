# Agent notes

Read [PLAN.md](./PLAN.md) first: what Motherload is, what the maintainer decided, the content mapper facts and where each was confirmed, the steps, and what is open. [DESIGN.md](./DESIGN.md) holds one section per design decision with its alternatives and evidence; a change to a decision updates its section.

The Motherload package types data-file imports (`.toml`, `.yaml`/`.yml`, `.json5`, `.jsonc`, `.env`, `.csv`, `.tsv`, `.txt`, `.md`) and `.schema.jsonc` and `.schema.json5` imports (a type plus a validator): a TypeScript 7.1 content mapper, a preload and bundler plugins. Its sibling products are dotsql (`~/Documents/projects/dotsql`, the `.sql` loader) and porg (`~/Documents/projects/lando`, the porg repository: the reactive Postgres driver, `pg_porg` and live queries). Read those repositories; do not write to them.

## Layout

| Path | What it is |

It is built to static files with Vite and React Router (`nub run build` writes `site/build/client`, which the Vercel project `motherload` serves; `site/vercel.json`), on Fumadocs and Twoslash, with the table of contents on the left; a project of its own, with its own lockfile. The root `package.json` links `motherload` to the repository root (`link:.`), because a mapper package does not resolve through self-reference, links each `packages/<name>` as `@motherload/<name>`, and links the template's `universal-toml` and `universal-toml-2` the same way. It also lists every package's parser, from which the linked sources resolve them, so one `nub install` at the root serves them all; there is no workspace. Every `package.json` in the repository is private and points at TypeScript sources; only `dist/` is published.

## JavaScript: nub

Prefer `nub` over `node`, `bun`, `npm`, `npx`, `pnpm` and `yarn`: run files with `nub <file>`, package scripts with `nub run <script>`, local CLIs with `nubx <tool>`, installs with `nub install` and `nub add`. The lockfile (`pnpm-lock.yaml`) is respected both ways. Use `nub --node <file>` for strict, unaugmented Node; nub's own loaders for `.toml`, `.yaml`, `.json5` and `.jsonc` are off there, which is what a check of Motherload's preload wants.

- Running `nub run typecheck` type-checks the sources and runs the content mappers on `lab/universal/app`, `lab/basic` and `lab/packages` (`tsc --runExternalCode`).
- Running `nub run build` writes `dist/`, and `nub run check-dist` then installs it outside the repository and runs it.
- Running `nub run test` runs `tests/**/*.test.ts` with `node --test`.
- Running `nub run dev` in `site/` serves the docs site on port 3312; `nub run build` there fails when a page example stops type-checking.
- Setting `TS_CONTENT_MAPPER_DEBUG=1` on `nubx tsc -p lab/basic/tsconfig.json --noEmit --runExternalCode` prints the JSON-RPC traffic.
- The nub installer refuses a package version younger than 24 hours (`minimumReleaseAge`); the TypeScript nightly is pinned to one that passed it. Do not bypass the gate.

## Git

Work lands on `main` directly, with no branch or pull request. When a task is done and `nub run typecheck` and `nub run test` pass, commit it to `main` and push it to `origin` without asking. The push may also carry commits another session left unpushed on `main`; push them with it. Several sessions can work in this checkout at once, so stage only the files the task changed.

A release is never cut by a push: run `nub run bump <version>`, commit and push it, then `gh workflow run release.yml -R colinhacks/motherload`, approve the run's `npm` deployment, and ask the maintainer to run `stager` in a terminal, which approves every staged version under one authenticator code and resumes the run ([DESIGN.md](./DESIGN.md#releasing)).

## Writing conventions

The product is Motherload, capitalized, in prose and in every message a user reads; `motherload` is the npm package, the import specifier, the diagnostic source and the Standard Schema vendor, always as code. Its icon is three stacked gold bars, drawn as an SVG (`site/public/icon.svg`, the favicon, and the same drawing in `site/public/motherload.svg`): the site's favicon, the top of its left column, and the README's title. Never hard-wrap Markdown: every paragraph, list item and table row is one line. Never put three paragraphs in a row on the docs page: three or more short facts or rules are a list, each item opening with a bold label, as the `.schema.jsonc` and `.env` sections have them (the maintainer, 2026-10-20: "Never, ever have three paragraphs in a row like this. This looks like shit"). Never estimate developer time. Anything stated as fact traces to a file read or a command run; a guess goes in PLAN.md's Open section as a question. Call the repository at `~/Documents/projects/lando` the porg repository.
