# Motherload: the plan

Import a data file and get a typed module: `.toml`, `.yaml`/`.yml`, `.jsonc`, `.json5`, `.csv`, `.tsv`, `.txt`, `.md` and `.env` become modules of data with no run time. One npm package of TypeScript 7.1 content mappers, with a preload and bundler plugins so the same import runs. The brand study behind the name is `docs/brands.md` in the porg repository (`~/Documents/projects/lando`), also copied to dotsql (`~/Documents/projects/dotsql/docs/brands.md`); [DESIGN.md](./DESIGN.md) records every decision taken while building the first version.

## Decisions

The maintainer's, Colin McDonnell, on 2026-10-03:

- **One npm package, Motherload,** of TypeScript 7.1 content mappers (plus bundler plugins and a preload) that type the data files a project imports: `.toml`, `.yaml`/`.yml`, `.jsonc`, `.json5`, `.env` and `.schema.json` (`.schema.jsonc` and `.schema.json5` from 2026-10-20 until JSON Schema left for dotschema on 2026-10-21, below), with `.csv`, `.tsv`, `.txt` and `.md` (with its frontmatter) added on 2026-10-06. The name's pun on "load" is deliberate.
- **A data file becomes a module of data with no run time,** so Motherload is a development dependency of an application that bundles.
- **The SQL loader is not part of Motherload.** It is its own product, dotsql (`~/Documents/projects/dotsql`), with each SQL dialect's engine in an add-on under `@dotsql`. A project that imports both lists both in its tsconfig, each with its own extensions.
- **Porg** (`~/Documents/projects/lando`, the porg repository) is the reactive Postgres driver, `pg_porg` and live queries.
- **The loader kit stays a template,** not a published package: [lab/universal](./lab/universal), copied here from dotsql because Motherload's mappers are its first users.
- **Build an initial working version,** deciding every design question and recording it in DESIGN.md, one section per decision; the maintainer iterates on the design afterwards.
- **A per-import choice between the parsed data and the raw text, and literal types as an opt-in,** with a query on the specifier (`?raw`, `?const`) proposed and to be verified against TypeScript first. It was: TypeScript does not resolve a specifier with a query, so the choice was by export name ([DESIGN.md](./DESIGN.md#how-an-import-chooses)); revised on 2026-10-06, below.

- **A data file's default export is typed as `as const` would type it,** and `?raw` gave the file's text, typed by `motherload/client`, until the maintainer removed it on 2026-10-20, below ([DESIGN.md](./DESIGN.md#the-module-an-import-returns)).
- **A YAML file of several documents stays the list of them,** typed the same as one document whose value is a list; no `documents` export ([DESIGN.md](./DESIGN.md#the-yaml-parser-yaml)).
- **A `.env` file is imported for its effect,** `import "./.env"`: its variables are set on `process.env` when the module runs and typed on `NodeJS.ProcessEnv`, with no value in a bundle ([DESIGN.md](./DESIGN.md#the-env-module)).

The maintainer's, on 2026-10-08 and 2026-10-09:

- **Motherload becomes a family of packages** released together at one version: a package per format under `@motherload` (`toml`, `yaml`, `json5`, `jsonc`, `env`, `csv`, `txt`, `md`, and `schema` until 2026-10-21), each with its own mapper, preload, esbuild plugin and parser; `motherload`, the package of all of them, with one of each; and `@motherload/core`, the code they share, published as their dependency. Every dependency is at an exact version ([DESIGN.md](./DESIGN.md#packaging)).
- **The per-format `dot<ext>` names stay reserved;** the `@motherload` scope replaces them.

The maintainer's, on 2026-10-19 and 2026-10-20:

- **A `.md` file's default export is the object `{ md, frontmatter }`:** its body, a string, and its frontmatter, typed as `as const` would type it, each also a named export. The default is there so that the import hovers with its whole type, which a namespace import (`import * as post`) never does in TypeScript. It replaced, the same day, a module of the named exports with no default, which had replaced the default export of the body as a string. The body rendered as HTML is left for later ([DESIGN.md](./DESIGN.md#the-txt-and-md-modules)).
- **No `?raw`,** the maintainer's decision of 2026-10-20: "I'm not sure this is worth including right now. We shouldn't document it. And we should probably just remove it. We'll see if anyone asks about it later." An import of a data file has one form, its default export; a query or hash on it goes to the next hook or plugin. The `?raw` query had needed a `types` entry in every project's tsconfig, because TypeScript hands no query to a content mapper ([DESIGN.md](./DESIGN.md#the-module-an-import-returns)).
- **Every data module is an ES module,** whatever the nearest package.json says, the maintainer's preference of 2026-10-20: "I definitely have a strong preference for going ESM first here." The mapper reports `.mts`, so an ES module's default import of a data file in a package with no `type` is the data, as it is at run time ([DESIGN.md](./DESIGN.md#the-module-an-import-returns)).

The maintainer's, on 2026-10-21:

- **JSON Schema leaves Motherload for a package of its own, dotschema** (`~/Documents/dotschema`): "I'm trying to decide whether to extract the JSON schema into its own package, something like `dotschema`. I think it's cleaner to extract it personally. It's not really the same as the data loading that we do in the other stuff. Let's go ahead and do it." Then: "The new package doesn't need a documentation site. It can just have a README." And: "We could always add support into Motherload later and give Motherload a dependency on dotschema, but not right now." So Motherload is eight data formats with no dependency on dotschema; the docs page points a `.schema.jsonc` import at dotschema, as it points a `.sql` import at Reylo, and the README does too; and the schema decisions and their Open items moved to dotschema's PLAN.md. It replaces the answer of earlier that day, "Keep it in `motherload`" ([DESIGN.md](./DESIGN.md#json-schema-left-for-dotschema)).

## Content mapper facts

Each was a lead from earlier research; each row says where it was confirmed. "Measured" means probe mappers in a scratch project, on TypeScript `7.1.0-dev.20260918.1` and `7.1.0-dev.20261002.1`, with the same behaviour on both ([DESIGN.md](./DESIGN.md#the-typescript-build)). The protocol is microsoft/typescript-go PR [#4712](https://github.com/microsoft/typescript-go/pull/4712).

| Fact | Confirmed |
| --- | --- |
| A tsconfig `contentMappers` entry is `{ package, extensions[], options? }` | The porg repository's `DESIGN.md` (its table of verified mapper facts); measured: entries without `options` work, and an entry's `options` reach `openProject` |
| TypeScript runs one process per mapper package and version | The porg repository's `docs/prior-art.md` section 4a, quoting the PR: processes are deduplicated "by resolved package name and version"; measured: two entries of one package start one process, which answers `openProject` once per entry |
| The process starts lazily | Measured: with no matching file in the program, a mapper without `dynamicConfig` started no process, with or without `--incremental` |
| One owner per extension | The porg repository's `docs/universal-plugin.md` section 1 (copied here as [docs/universal-plugin.md](./docs/universal-plugin.md)); measured: `TS100022` on 20260918.1, renumbered `TS18067` on 20261002.1 |
| The longest suffix wins, so `.config.toml` can belong to another mapper than `.toml` | `docs/universal-plugin.md` section 1 (`GetLongestExtensionFromPath`); measured: `.config.toml` in one mapper and `.toml` in another, in both orders, each file reached its own mapper |
| `.json` itself cannot be claimed, nor, from the nightly after 2026-10-13, a suffix that ends in it | Measured: `TS100021` / `TS18066`, "a built-in extension and cannot be registered by a content mapper"; `.schema.json` could be claimed beside `resolveJsonModule` on both builds and on `7.1.0-dev.20260929.1`, and gets TS18066 on `7.1.0-dev.20261019.1` (microsoft/TypeScript#64581, measured on 2026-10-19), so the schema suffixes, dotschema's since 2026-10-21, are `.schema.jsonc` and `.schema.json5`, which the rule's pattern, `/\.(?:[cm]?[jt]s|[jt]sx|json)$/i` in the PR, leaves alone (measured on the released `7.1.0-beta` on 2026-10-20, where `.schema.json` gets TS18066 too) |
| Plain `.json` is typed by `resolveJsonModule` | Measured: `{ port: number }` for `{ "port": 8080 }`; under `module: nodenext` an ES module needs `with { type: "json" }` (`TS1543` without it) |
| `dynamicConfig` is one flag per package | The porg repository's `DESIGN.md`: it sits in the package's `package.json` under `typescript.contentMapper`; its `docs/brands.md` ("The `dynamicConfig` flag is per package") |
| `tsc --incremental` opens dynamic mappers' projects | The porg repository's `docs/prior-art.md` section 4b, quoting the PR ("TypeScript uses `openProject` to obtain `configIdentity` before an up-to-date decision"); measured: a `dynamicConfig` mapper started and answered `openProject` on each `--incremental` run with no matching file present |
| A generated module can import another file the same mapper claims: TypeScript sends that file through the mapper too and follows it through a change, with no `dynamicConfig` | Measured on 20261002.1 on 2026-10-20 with a probe mapper whose `a.probe` module imports the type of `./b.probe`, which `main.ts` does not import: one run typed it; `--incremental` runs, with the build info written, transformed both files on every run, the run with nothing changed included; under `--watch`, one process transformed both again on each change to `b.probe`, and the error in `main.ts` followed its value |
| The failure budget is 5 per mapper, and each tsconfig entry is its own mapper | The porg repository's `DESIGN.md` (the PR's text: "after five failures in a project tsc stops calling that mapper") and `docs/brands.md` (per entry, read in the source, not run); measured: one entry with seven failing files gave five failed transforms and then the switched-off diagnostic, while the same package in two entries took four failures each without being switched off |
| A transform request carries only `fileName`, `content` and `projectHandle` | Measured; `openProject` carries `configFileName`, `projectHandle`, `compilerOptions`, and `options` when the entry has them |
| A mapped file's module format comes from the extension the mapper reports and the nearest package.json's `type`, as a real file's does | Read on typescript-go's main on 2026-10-20 (`internal/compiler/filesparser.go`); measured on 20261002.1: `.ts` in a package with no `type` is CommonJS, `.mts` an ES module |
| A scoped package (`@probe/loader`) is a content mapper like any other | Measured on 20261002.1: its tsconfig entry started its mapper, which typed a `.toml` import |
| A specifier with a query (`./x.toml?raw`) does not resolve to the file, so the mapper never sees it | Measured: `TS2307` on both builds; an ambient `declare module "*.toml?raw"` types it instead (measured on 20261002.1); read again on typescript-go's main on 2026-10-20, whose transform request holds `fileName`, `content` and `projectHandle` and whose resolver has no handling for a query; details in [DESIGN.md](./DESIGN.md#how-an-import-chooses) |
| tsrs, oxc's Rust port of the TypeScript 7 compiler ([oxc-project/tsrs](https://github.com/oxc-project/tsrs)), runs Motherload's mapper as tsc does, from the command line but not in its language server | Measured on 2026-10-21 with `tsrs@0.18.0-ts7.1.0-dev.20260929` (TypeScript `7.1.0-dev.20260930.4`): with `--runExternalCode` it passed `lab/basic`, `lab/packages` and `lab/universal/app`, failed a wrong assertion added to a copy of `lab/basic`, and printed for `tests/fixtures/errors` the same output as tsc, byte for byte; `--incremental`, `-b` and `--watch` work too, and under `--watch` a change to a `.toml` file brought its type errors and the change back took them away. Its `docs/LSP.md`: "The server does not run content mappers yet" |

## What works

Run `nub install`, then `nub run typecheck` and `nub run test` (53 tests). The suite type-checks [lab/basic](./lab/basic) through the content mapper with exact-type assertions and a failing control, checks diagnostics placed in broken files, runs `lab/basic` under the preload, and bundles it with the esbuild plugin into a file that imports nothing; it does the same for [lab/packages](./lab/packages) on two format packages alone, and checks that the JSONC and JSON5 loaders defer to a loader of another package claiming a longer suffix, as dotschema's does, in Node, Bun and esbuild. Running `nub run build` writes the packages to `dist/`, and `nub run check-dist` installs them from tarballs outside the repository and runs both labs on them. [AGENTS.md](./AGENTS.md) lists the layout.

## Steps

1. **The template, the package and the plan** (done on 2026-10-03).
2. **The mapper core from the template** (done on 2026-10-03): the contract in `src/universal.ts` and the server in `src/rpc.ts`, in `packages/core/src/` since 2026-10-20, with the changes listed in [DESIGN.md](./DESIGN.md#the-starting-point-the-loader-template).
3. **Each format** (done on 2026-10-03): TOML, YAML, JSON5, JSONC and `.env`, each with a parser chosen in DESIGN.md. CSV, TSV, text and Markdown with frontmatter added on 2026-10-06 ([DESIGN.md](./DESIGN.md#the-csv-and-tsv-module)).
4. **The schema loader** (done on 2026-10-03, and moved to dotschema on 2026-10-21, [above](#decisions)).
5. **Bundler plugins and the preload:** the preload (`motherload/register`) and esbuild (`motherload/esbuild`) are done. Next: Vite, Rollup and Rolldown through the template's unplugin adapter, webpack, Rspack and Turbopack through its webpack-loader adapter, Bun run for real, and a Jest transformer as dotsql has (a preload does not reach Jest's test code, [DESIGN.md](./DESIGN.md#what-runs-where)). Each needs a lab project that runs it.
6. **The package family and a build to `dist/`** (done on 2026-10-20, the maintainer's answer that day: "Build them, then document them in Setup"): `@motherload/core`, eight format packages in [packages/](./packages) (nine until the schema package left on 2026-10-21) and `motherload` combining them ([DESIGN.md](./DESIGN.md#packaging)); `nub run build` compiles each to JavaScript and declarations in `dist/<dir>`, since the repository's manifests point at the TypeScript sources, which Node runs directly, as dotsql's repository does. The docs page's Setup documents the packages under "Loaders à la carte".
7. **Docs and a launch:** a README for users, a docs site (a first draft of one page is in [site/](./site), for the maintainer to review), the first release from `"private": true` to published (0.0.1, published on 2026-10-21 by `.github/workflows/release.yml`, [DESIGN.md](./DESIGN.md#releasing)).

## Open

- **`.env` files:** whether to expand `${VAR}` as nub does; how a project claims `.env.local` and `.env.production`, whose suffixes are not `.env`.
- **TOML date-times:** local dates and times are ISO strings and offset date-times are `Date`s; Temporal types (`Temporal.PlainDate` and the rest) are the alternative once every target runtime has Temporal.
- **JSONC trailing commas:** allowed today; whether a `.jsonc` file should be refused for them.
- **CSV quoting in TSV:** a `.tsv` file follows the IANA registration, with no quoting; whether the TSV that spreadsheets export puts quotes around a field that holds a tab or a line break, and so needs CSV quoting, is unverified.
- **Large CSV files in a bundle:** each row is an object literal that repeats every column name; an array of arrays mapped to objects when the module runs would be smaller.
- **Markdown:** whether `.mdx` should be claimed, whether a `+++` TOML frontmatter (Hugo's) should be read, and whether a `.md` module should also export its body rendered as HTML or as an AST (the maintainer, on 2026-10-20: "down the line", not now, and later that day: "We could just wait to see what people ask for"). Either would be made when the module is built, so a bundle carries no renderer and leaves out an export it does not import ([DESIGN.md](./DESIGN.md#the-txt-and-md-modules)); which renderer, and whether a project sets its options (GFM, heading ids, highlighting), is open.
- **Vite and `.json5`:** on Vite's main branch the JSON transform is rolldown's native `builtin:vite-json`, which takes only ids that end in `.json`, but Vite's `isJSONRequest`, `\.(?:json|json5)(?:$|\?)` (`packages/vite/src/node/plugins/json.ts`), still sends a `.json5` id's code, in a module runner's SSR transform with `json.stringify: true` and `namedExports` off, through `ssrTransformJSON`, which replaces the first `export default` with an assignment in place of transforming the module (read on 2026-10-20, not run). Whether that breaks the module Motherload returns, which has one `export default` and no `import`, is unverified until the Vite plugin exists.
- **The built-in data loaders of nub** cover `.toml`, `.yaml`, `.json5` and `.jsonc` with a default export only; whether nub should read Motherload's preload from its package (the template's `nub` manifest proposal in docs/universal-plugin.md section 5). On 2026-10-20 nub 0.9.6 refused `.json5` and `.jsonc` with `ERR_UNKNOWN_FILE_EXTENSION`, inside the repository and outside it; what turns nub's own loaders on or off was not found.
- **The TypeScript nightly:** the repository pins `7.1.0-dev.20261002.1`; the content mapper diagnostic codes changed between nightlies, so tests match messages, not codes. A nightly after 2026-10-13 refuses an extension that ends in a built-in one; Motherload registers none (`.schema.json` was the one, until 2026-10-19), and on `7.1.0-dev.20261019.1` and on the released `7.1.0-beta` the projects of `nub run typecheck` passed and `tests/fixtures/errors` gave the same diagnostics as on the pinned build (run on 2026-10-20, when Motherload still read schemas).
- **The published schema package:** `@motherload/schema` 0.0.1 was published on 2026-10-21, one of the eleven packages release run 39560615518 staged with provenance and the maintainer approved ([DESIGN.md](./DESIGN.md#releasing)), and `motherload@0.0.1` depends on it; no later release will publish it, since the package left the repository the same day; whether to deprecate it there with a message that points at dotschema is open, and so is how the release notes of the next `motherload`, which reads no schema, say so.
